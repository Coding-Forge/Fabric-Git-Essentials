Part 1: Standards Foundation

Learn how to define governance standards and quality rules that your entire organization will follow.

Duration: 8-12 minutes | Tools: 4 | Theme: Defining What "Good" Means

📢 Opening Narration
Welcome to the Fabric BI DevOps Accelerator Toolkit. This is Part 1, where we learn how to build governance standards.

Every organization has different rules about how reports should look, how measures should be documented, and what makes something production-ready. Part 1 is about capturing those rules and making them automated.

By the end of this part, you'll have defined standards that your entire organization can use, and you'll have tools that enforce them automatically in your CI/CD pipeline.

Tool 1.1: Launchpad Overview

The starting point for exploring all 16 toolkit tools

⏱️ 1 min
📢 What is the Launchpad?
The Launchpad is your entry point to all 16 tools in this accelerator. When you open it at localhost 8000 tools index.html, you'll see four main workflow categories. Each category groups related tools that work together to solve a business problem.

The 16 tools work together in a recommended sequence: Part 1 tools define your standards, Part 2 tools help reviewers assess changes, and Part 3 tools make governance scale across your organization.

Demo Actions (Practice speaking as you do this):

  1. Navigate to localhost:8000/tools/index.html
  2. Point out the four workflow sections
  3. Count the 16 tools visible
  4. Say: "Here are all 16 tools we're going to explore"
Key UI Elements:
• "Fabric BI DevOps Accelerator" title
• 16 tool cards in a grid layout
• Each tool has: Name, Description, Link
• Grouped into workflow categories

Tool 1.2: Enterprise Standards Builder

Define quality policies and governance standards

⏱️ 3-4 min
📢 What Does It Do?
The Enterprise Standards Builder is where your organization captures 'what good looks like' in one place. You define policies for your reports, your datasets, and your entire BI platform.

Instead of those rules living in PowerPoints and emails that nobody reads, you capture them here, and the system enforces them automatically. The builder lets you choose which policies to enable, customize them for your needs, and generate policy files that your CI/CD pipeline will check against.

Demo Actions (Practice narration):

  1. Click "Use starter policy" to load a pre-built example
  2. Show the Profile dropdown (select "Standard" profile)
  3. Point out the policy controls (checkboxes for each policy)
  4. Say: "This profile has 12 policies enabled for reports and 8 for datasets"
  5. Click "Download policy profile" button
  6. Say: "This downloads to a JSON file your pipeline will use"
Key UI Elements:
• Profile dropdown (Minimal, Standard, Advanced, Custom)
• Policy controls (checkboxes)
• Report policies section
• Dataset policies section
• "Download policy profile" button

Tool 1.3: Rule Designer

Create custom DAX and governance rules

⏱️ 3-4 min
📢 Customizing Rules
The Rule Designer lets you create custom rules beyond the built-in policies. Maybe you want to enforce a specific naming convention for measures, or require that every visual has a title, or check that no report uses deprecated DAX functions.

You define these rules once in the Rule Designer, then they're checked automatically on every PR. No manual review needed.

Demo Actions (Practice narration):

  1. Click "Use starter rules" to load examples
  2. Show the rule list with multiple rules visible
  3. Click on one rule to show details (Rule name, category, description, implementation)
  4. Say: "Here are 15 custom rules already defined for this organization"
  5. Click "Download rules JSON" button
Key UI Elements:
• Rule name field
• Category dropdown (Report, Dataset, Governance)
• Rule definition/description
• Implementation details
• "Download rules JSON" button
• Rule list view

Tool 1.4: DAX Test Builder

Define automated tests for DAX logic

⏱️ 3-4 min
📢 Testing Data Logic
The DAX Test Builder is where you define automated tests for your measures and calculations. You describe: Given this scenario with these values, what should the measure return?

These tests run automatically on every PR. If someone changes a measure and the test fails, the PR gets blocked. This catches logic errors before they reach production.

Demo Actions (Practice narration):

  1. Click "Use sample tests" to load examples
  2. Show the test list (multiple tests for different measures)
  3. Click on a test to show: Measure name, Input values, Expected result, Actual result
  4. Show the test health summary (passed/failed counts)
  5. Click "Download test suite"
Key UI Elements:
• Test health panel (Passed/Failed/Total)
• Measure name field
• Test input values
• Expected result field
• "Download test suite" button
• Test list view
✅ You've completed Part 1! You now have standards defined, custom rules created, and tests in place. These are the foundation for everything else.

Part 2: PBIP Review & Pull Requests

Learn how report authors prepare changes and reviewers assess them efficiently.

Duration: 13-18 minutes | Tools: 5 | Theme: Context-Aware Code Review

📢 Opening Narration
Welcome to Part 2. You now know how standards are defined. The question is: How do you enforce them when a team wants to deploy changes?

Part 2 shows how report authors prepare pull requests for review and how reviewers understand what changed without reading raw JSON. We're moving from 'code review is tedious' to 'code review is actually fast because I have the context I need.'

Tool 2.1: Deployment Manifest Builder

Create the release contract for your deployment

⏱️ 3-4 min
📢 What is a Deployment Manifest?
Before any change is deployed, you need a release contract that answers: What is being deployed? Who owns it? Where does it go? What governance checks must pass?

The Deployment Manifest Builder creates this contract in one place. It becomes part of your PR description so reviewers understand the deployment context from the start.

Demo Actions (Practice narration):

  1. Click "Use starter manifest"
  2. Show Solution Identity (name, domain, criticality, owners)
  3. Scroll to Ownership section
  4. Scroll to Artifacts section (what's being deployed)
  5. Show Validation Gates (what checks must pass)
  6. Click "Download manifest summary"
Key UI Elements:
• Solution name field
• Domain dropdown
• Criticality (low/medium/high)
• Business owner / Technical owner
• Artifacts list
• Validation Gates
• "Download manifest summary" button

Tool 2.2: PBIP Project Readiness Scanner

Pre-PR quality checkpoint for report authors

⏱️ 2-3 min
📢 Catching Issues Early
The readiness scanner runs on a report author's local PBIP folder and catches missing structure or governance assets BEFORE opening the PR.

If something is wrong—missing test files, incomplete metadata, configuration issues—the scanner tells you. No surprises at review time. This prevents PR delays and frustration.

Demo Actions (Practice narration):

  1. Click "Use sample scan"
  2. Show Readiness Score (XX%, Blockers, Warnings, Passed)
  3. Say: "Zero blockers means we're ready for review"
  4. Click "Findings" tab
  5. Show findings by category
  6. Click "Download Markdown report"
Key UI Elements:
• Readiness Score panel
• Blockers count
• Warnings count
• Passed checks count
• Findings tab
• "Download Markdown report" button

Tool 2.3: PBIP Diff Viewer

Translate JSON changes into business language

⏱️ 2-3 min
📢 Understanding Changes
Raw PBIP diffs are unreadable JSON. The PBIP Diff Viewer translates them into business language. Instead of looking at raw files, reviewers see: What reports were added? What measures changed? What governance assets were updated?

This is where PR review becomes efficient.

Demo Actions (Practice narration):

  5. Show different artifact types
  6. Click "Download Markdown"

• Diff Health panel
• Changed/Added/Removed counts
• Artifact type filter
• Search for file paths
• Changed artifacts list
• "Download Markdown" button

Tool 2.4: Dependency Impact Analyzer

Show what tests are needed for changes

⏱️ 2-3 min
📢 Predicting Downstream Impact
If I change a measure, which reports and visuals are affected? Which ones need re-testing?

The Dependency Impact Analyzer answers these questions. It prevents the nightmare scenario: You deploy a measure change that looks safe, but it breaks five reports in production.

✅ You've completed Part 2! Now reviewers have all the context they need to assess changes quickly and confidently.

Part 3: Platform & Governance at Scale

Learn how to make governance work for your entire organization across all CI/CD platforms.

Duration: 22-28 minutes | Tools: 8 | Theme: Making Governance Invisible

📢 Opening Narration
Welcome to Part 3. You've learned how individuals and teams handle governance and code review. Now the platform team's job begins.

How do we automate this at scale? How do we generate CI/CD pipelines that work on Azure DevOps, GitHub, and GitLab simultaneously? How do we track exceptions and measure program success?

This is where governance moves from 'check you did the right thing' to 'the system does the right thing automatically.'

Tool 3.1: Pipeline Config Generator

Generate CI/CD pipelines for all three platforms

⏱️ 3-4 min
📢 Multi-Platform Governance
Instead of maintaining separate Azure DevOps, GitHub Actions, and GitLab CI configurations, you define the workflow once and generate all three platform versions automatically.

One workflow definition, three platform implementations. No drift, no inconsistency.

  3. Show Validation Stages (5 stages)
  4. Show Platform-Specific Config
  5. Click "Generate Azure DevOps YAML" (show briefly)
  6. Click "Generate GitHub Actions YAML" (show briefly)
  7. Click "Generate GitLab CI YAML" (show briefly)
Key UI Elements:
• Pipeline name field
• Trigger events
• Validation Stages section
• Platform-Specific Config
• "Generate Azure DevOps YAML" button
• "Generate GitHub Actions YAML" button
• "Generate GitLab CI YAML" button

Tool 3.2: Policy Exception Register

Track governance waivers and exceptions

⏱️ 3-4 min
📢 Managing Exceptions
Teams will ask for exceptions to rules. Maybe they say 'Our situation is special—we need a waiver on this quality check to ship today.'

Instead of hiding those exceptions, you track them. What rule? Why? Who approved? When does it expire?

This creates visibility. If 80% of exceptions are for the same rule, that tells you the rule might be wrong.

Demo Actions (Practice narration):

  1. Click "Use starter register"
  2. Show Register Health (Active, Expiring, Expired)
  3. Click on an exception to show details
  4. Show expiration tracking
  5. Filter by status (Active, Expiring, Expired)
  6. Click "Download register report"
Key UI Elements:
• Register Health panel
• Active exceptions count
• Expiring soon count
• Expired count
• Exception list
• Status filter
• "Download register report" button

What rules is a specific team actually following? This generator merges: your base rules, their exceptions, their overrides. It answers: Here's exactly what this team must follow.

• Merged ruleset output
• "Download effective rules" button

Tool 3.5: Release Readiness Dashboard

Objective release gate

⏱️ 2-3 min
📢 Go / No-Go Decisions
Before you deploy to production, is the solution actually ready? The Release Readiness Dashboard tracks four gates: Quality rules passed? Readiness score above threshold? No blocking exceptions? All approvals signed off?

When all four are green, you release. When one is red, you stop. This removes guessing from release decisions.

Demo Actions (Practice narration):

  3. Show all 4 Release Gates (all green)
  4. Show Solution Timeline
  5. Click "Approve for release"
  6. Click "Download release summary"
Key UI Elements:
• Readiness Score panel
• Current score percentage
• Days to release
• 4 Release Gates (Quality / Readiness / Exceptions / Approvals)
• Solution Timeline
• "Approve for release" button
• "Download release summary" button

🎉 Closing Remarks

📢 Closing Narration (Practice this at the end)
You've now seen the complete Fabric BI DevOps Accelerator toolkit. 16 tools across three workflows.

Part 1 was standards. Part 2 was review. Part 3 was scale.

But here's the real insight: None of these tools enforce anything by themselves. The enforcement happens in your CI/CD pipeline, in your code review process, in your release gates. The tools just make the process visible and fast.

That visibility and speed compound. After six months, you realize: We're releasing 40% faster. We're catching issues earlier. We're onboarding teams in 10 days instead of 30. We're moving teams from 'we can't deploy safely' to 'we deploy every day.'

That's the promise of integrated governance automation. Thank you for walking through the toolkit with us.
